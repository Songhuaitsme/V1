## 0. 本文回答的问题

本文把“任务到来后系统到底做什么”明确为可执行流程，回答：

1. 同一周期多个任务先处理谁；
2. 单个任务是否需要主动等待；
3. 预测窗口如何确定；
4. 如何在窗口内生成节点—时间—路径候选；
5. 哪些条件属于硬过滤；
6. DQN如何评价可变数量候选；
7. 如何一次性提交CPU和带宽预约；
8. 预约时估计与完成时实现指标如何区分；
9. 如何证明主动等待真正有价值。

核心结论：

> 系统不先做一个独立的“等/不等”二元判断。系统先在任务允许的完整启动窗口内生成所有可行候选，再从中选择一个候选。若所选候选晚于最早可行开始时间，就自然构成主动等待。

## 1. 职责边界

目标系统分为七个逻辑组件：

```text
TaskQueueManager
    负责到达、Queued、Pending、Expired和确定性任务顺序

ForecastProvider
    提供允许窗口内的外生电价和绿电轨迹

ReservationCalendar
    保存CPU与每条链路的半开区间预约，支持精确峰值查询

CandidateGenerator
    生成并过滤节点—时间—路径候选，只输出可提交候选

CandidatePolicy
    在可行候选中选择；可以是最早基线、启发式或候选DQN

ReservationManager
    在一致资源快照上重新验证并原子提交CPU/BW预约

EventEngine + MetricsLedger
    推进传输/运行/完成事件，核算实现成本、绿电和正式指标
```

边界原则：

- 队列管理器决定“下一个处理哪个任务”；
- 候选生成器决定“哪些方案物理可行”；
- 策略决定“可行方案中选哪一个”；
- 预约管理器决定“选中方案能否原子提交”；
- 事件引擎决定“任务何时真正传输、运行和完成”；
- 指标账本决定“最终实现结果是什么”；
- 任何组件不得通过一个人工总分绕过其他组件的硬约束。

## 2. 核心数据对象

### 2.1 Task

```text
Task:
    task_id
    arrival_time                 # 仿真时间单位
    source_node
    cpu_demand
    execution_duration           # 仿真时间单位
    cpu_work_sim_units
    data_size_mb                 # 十进制MB
    bandwidth_demand_mbps
    sla_type
    preferred_start_limit        # 仿真时间单位，Soft/Flexible必需
    latest_start_limit           # 仿真时间单位，所有类型均有绝对边界
    state
    pending_attempts
    failure_retry_count           # 第一阶段固定为0；为后续重规划阶段预留
```

派生字段：

```text
absolute_preferred_start = arrival_time + preferred_start_limit
absolute_latest_start = arrival_time + latest_start_limit
```

`pending_attempts`只用于观测候选搜索次数；`failure_retry_count`为后续真实故障重规划预留。二者都不得作为任务业务优先级的直接加分项。

第一阶段预约不可取消/重规划，因此真实传输或运行故障直接进入`Failed`，不重新预约，`failure_retry_count`保持0。原子提交冲突不是任务运行故障，单独使用`commit_attempts`并受每次决策最大尝试数约束。

## 3. 每个调度周期的完整流程

设当前周期时间为`t`：

```text
on_scheduling_cycle(t):
    1. EventEngine.advance_to(t)
       - 开始到时传输
       - 传输结束后开始计算
       - 计算结束后置Completed并核算实现指标

    2. 接收arrival_time <= t的新任务
       - 校验字段
       - 合法任务进入Queued
       - 队列真实溢出则Rejected(SCHEDULER_QUEUE_CAPACITY)

    3. 处理绝对期限
       - 已经过期且未Reserved的任务进入Expired
       - 到期原因单独记录

    4. 构建本周期eligible任务集合
       - 新到达/尚未决策的Queued任务
       - 仅在“可能改善可行性”的事件后重新激活的Pending任务

    5. 按queue_order_key确定性排序

    6. 依次处理最多MAX_DECISIONS_PER_CYCLE个任务
       - 候选非空时策略必须选择一个候选，不存在Reject动作
       - 每个任务成功提交后立即更新预约日历
       - 后续任务看到最新日历
       - 未轮到的任务保持Queued

    7. 记录队列、状态、预约和硬约束不变量
```

第一阶段不是批量全局联合优化。任务顺序固定，DQN只选择当前任务的候选，因此不同策略可以在完全相同任务顺序下比较。

## 4. 如何选择下一个任务

### 4.1 到期检查

在排序前先计算：

```text
absolute_latest_start = arrival_time + latest_start_limit
```

- 若`t > absolute_latest_start`且任务未预约：进入Expired；
- 若`t = absolute_latest_start`：仍允许尝试恰好在边界开始的候选；
- 若边界时没有候选：立即Expired，不再进入Pending。

### 4.2 建议排序键

```text
queue_order_key(task) = (
    absolute_latest_start,
    sla_tie_rank,
    absolute_preferred_start_or_infinity,
    arrival_time,
    task_id
)
```

其中：

```text
sla_tie_rank = Hard:0, Soft:1, Flexible:2
preferred_start_time_or_infinity =
    absolute_preferred_start  # Soft/Flexible
    +infinity                 # Hard
```

按升序处理。

为什么绝对期限必须排在SLA类别前：

- Hard的绝对限制不可违反；
- Soft的120%绝对上限同样不可违反；
- Flexible也有系统承诺的绝对窗口；
- 固定给Hard乘大倍率，可能让远期Hard任务压过即将到绝对上限的Soft任务；
- EDF首先保护所有绝对边界，再用SLA类型打破相同期限的平局。

### 4.3 不进入排序的因素

以下因素不改变任务顺序：

- WAIT收益；
- 成本和绿电候选收益；
- DQN的Q值；
- `retry_count`；
- `pending_attempts`。

它们属于候选选择或诊断，不属于任务接纳公平性。

### 4.4 示例

当前时间为100秒：

| 任务 | 类型 | 绝对最晚启动 | 排序 |
| --- | --- | ---: | ---: |
| T1 | Hard | 106秒 | 1 |
| T2 | Soft | 110秒 | 2 |
| T3 | Flexible | 150秒 | 3 |

即使T3曾多次进入Pending，也不能凭`pending_attempts`压过T1和T2。

## 5. 如何确定单个任务的预测窗口

### 5.1 启动搜索窗口

对当前任务：

```text
decision_time = t
search_end = absolute_latest_start
```

各类型：

```text
Hard:
    latest_start_limit = hard_start_limit

Soft:
    preferred_start_limit = L
    latest_start_limit = 1.2L

Flexible:
    preferred_start_limit = L
    latest_start_limit = 1.5L
```

窗口不会在重试时重新从当前时刻开始计时，始终以原始`arrival_time`为基准。

### 5.2 启动窗口不等于预测数据终点

SLA限制的是计算开始时间，但候选成本和绿电需要覆盖整个执行区间。因此：

```text
latest_candidate_start = absolute_latest_start
latest_forecast_required = absolute_latest_start + execution_duration
```

CPU预约也可能延伸到启动SLA之后。ForecastProvider必须能为候选的完整`[compute_start, compute_end)`提供价格和绿电轨迹；否则候选不能获得完整评价。

### 5.3 时间离散

计算开始时间在调度网格上离散：

```text
grid_first = ceil_to_global_cycle(earliest_jit_start, scheduling_cycle, anchor=0)
grid_last = floor_to_global_cycle(absolute_latest_start, scheduling_cycle, anchor=0)
compute_start = grid_first + k × scheduling_cycle
```

绝对最晚启动是闭区间边界：边界对齐网格时必须包含；不对齐时以边界之前最后一个网格点为`grid_last`，不得插入非网格候选。浮点比较统一使用明确容差，不允许不同模块各自使用不同`1e-*`。

实现应使用整数tick而不是重复累加浮点周期：

```text
first_tick = ceil_with_shared_tolerance(earliest_jit_start / scheduling_cycle)
last_tick = floor_with_shared_tolerance(absolute_latest_start / scheduling_cycle)
compute_start(k) = (first_tick + k) × scheduling_cycle
0 <= k <= last_tick - first_tick
```

这样候选ID、理论槽数和截止边界不会随循环累积误差或枚举顺序变化。

正式模式的`time_grid`必须返回`grid_first`至`grid_last`之间所有对齐网格点，理论数量为`max(0, floor((grid_last-grid_first)/cycle)+1)`。不得用`MAX_LOOKAHEAD_SAMPLES`、均匀采样或人工Top-K跳过时间点。相对于声明路径生成器的完整网格是候选正确性的组成部分，而不是性能优化建议。

## 6. 如何生成节点—时间—路径候选

### 6.1 总体算法

```text
generate_candidates(task, decision_time, reservation_snapshot, forecast):
    candidates = []
    deadline = task.absolute_latest_start

    for node in allowed_compute_nodes:
        paths = topology.static_candidate_paths(
            source=task.source_node,
            target=node,
            bandwidth=task.bandwidth_demand
        )

        for path in paths:
            tx_duration = transmission_model(task, path)
            earliest_start = ceil_to_global_cycle(
                decision_time + tx_duration,
                scheduling_cycle,
                anchor=0
            )

            for compute_start in complete_time_grid(
                earliest_start, deadline, scheduling_cycle, anchor=0
            ):
                tx_start = compute_start - tx_duration
                tx_end = compute_start
                compute_end = compute_start + task.execution_duration

                if tx_start < decision_time:
                    continue

                if not bandwidth_calendar.feasible(
                    path, [tx_start, tx_end), task.bandwidth_demand
                ):
                    continue

                if not cpu_calendar.feasible(
                    node, [compute_start, compute_end), task.cpu_demand
                ):
                    continue

                if not sla_filter.feasible(task, compute_start):
                    continue

                metrics = estimate_candidate_metrics_over_interval(...)
                candidates.append(build_candidate(..., metrics))

    return validate_complete_candidate_set(candidates)
```

正式模式返回全部可行候选。若另行研究近似搜索，必须调用不同的显式入口，例如`generate_approximate_candidates(...)`，并在模型、回放和评估元数据中记录`candidate_mode=approximate`；不得在上述正式入口内根据规模静默采样。

### 6.2 路径和传输时长

第一阶段推荐固定带宽流水线模型：

```text
T_data_sec = data_size_mb × 8 / bandwidth_demand_mbps
T_prop_sec = Σ edge_distance_km / fiber_speed_km_per_sec
T_tx_sec = T_data_sec + T_prop_sec
T_tx_sim = T_tx_sec / seconds_per_sim_unit
```

静态候选路径首先删除任一边`capacity < bandwidth_demand`的路径。随后每个具体传输区间按预约边界检查路径各边的并发峰值。

### 6.3 CPU和链路可行性

对查询区间收集已有预约的全部开始/结束边界，拆成相邻半开子区间，并检查每个子区间：

```text
existing_peak + candidate_amount <= capacity
```

不能把只在不同子区间出现的预约直接相加。

### 6.4 SLA过滤

```text
start_delay = compute_start - arrival_time
```

Hard：

```text
start_delay <= hard_limit
```

Soft：

```text
start_delay <= 1.2 × preferred_limit

preferred_start_tardiness_ratio =
    clip(
        (start_delay - preferred_limit)
        / (latest_start_limit - preferred_limit),
        0,
        1
    )
    = clip((start_delay - preferred_limit) / (0.2 × preferred_limit), 0, 1)
```

Flexible：

```text
preferred_start_limit = L
latest_start_limit = 1.5 × L
start_delay <= latest_start_limit

preferred_start_tardiness_ratio =
    clip((start_delay - L) / (0.5 × L), 0, 1)
```

执行时长不进入当前启动SLA，但进入CPU预约和成本/绿能积分。

### 6.5 最早可行开始与最早候选集合

```text
s_earliest = min(candidate.compute_start)
earliest_candidates = {
    c | c.compute_start == s_earliest
}
```

主动等待：

```text
active_wait(c) = c.compute_start - s_earliest
```

“最早可行”只确定时间，不应靠任意节点编号决定同一最早时刻选择哪个节点。反事实基线应在`earliest_candidates`内使用与当前策略相同的成本—绿能偏好选择最佳候选，从而把“延迟收益”和“同一时刻换节点收益”分开。

### 6.6 无候选

```text
if candidates is empty:
    if decision_time >= absolute_latest_start:
        state = Expired
    else:
        state = PendingUncommitted
```

Pending任务不占资源、不算接受。

若候选非空，第一阶段的`CandidatePolicy`必须返回其中一个`candidate_id`。动作schema中没有`Reject`或“保持Pending”，策略不能因成本高、绿能低或Q值为负而放弃一个物理可行任务。字段非法、静态绝对不可承载和队列溢出由策略外的确定性规则处理。

完整窗口、不可取消预约和确定性资源日历下，单纯时间推进只会缩短窗口，不会创造新候选。因此第一阶段不做无变化逐周期重搜。只有以下事件可能重新激活：

- 预约事务回滚或资源故障恢复增加了容量；
- 拓扑或节点容量发生明确恢复；
- 后续阶段允许取消或重规划。

上一次搜索未覆盖完整窗口，只能作为显式`approximate`实验的重新激活原因，不适用于正式完整模式。

外生价格/绿电变化只改变候选优劣，不改变CPU/BW物理可行性，因此不会让“物理候选为空”变成非空。

## 7. 候选的评级依据

### 7.1 硬约束不参与打分

以下任一不满足，候选直接不存在：

- 传输不能在决策后开始并在计算前完成；
- 路径静态容量不足；
- 传输区间带宽不足；
- 计算区间CPU不足；
- 超过Hard或其他绝对启动上限；
- 预测数据不能覆盖完整计算区间；
- 字段、单位或路径非法。

不能给这些条件一个负分后仍交给DQN选择。

### 7.2 原始候选评价向量

每个可行候选保留原始量：

```text
V(c) = (
    candidate_marginal_system_cost_yuan,
    estimated_green_coverage,
    estimated_green_absorption_delta,
    projected_node_utilization,
    projected_path_peak_utilization,
    capacity_margin,
    start_delay,
    active_wait,
    preferred_start_tardiness_ratio
    preferred_start_tardiness_applicable
)
```

这些原始值是审计和Pareto分析依据，不能只保留一个总分。

### 7.3 归一化

建议：

- 绿能覆盖、容量余量和标准化迟到天然位于`[0,1]`；
- 成本按训练集或物理计费范围预先确定的尺度归一化；
- 系统吸纳增量按训练pilot确定的固定尺度裁剪；
- 开始延迟除以任务绝对启动限制；
- 不使用测试集min/max；
- 不建议只按当前候选集合min/max归一化，否则增加一个无关候选会改变其他候选特征。

### 7.4 经济成本和功率量纲

在v1.0已冻结的计费口径下：

```text
seconds_per_sim_unit = 86400 / traffic_day_duration_in_sim
task_power_mw = cpu_demand × cpu_power_unit_mw
dt_hours = dt_sim × seconds_per_sim_unit / 3600
cpu_work_cpu_hours = cpu_demand × execution_duration_hours

task_energy_mwh = Σ task_power_mw × overlap_dt_hours
economic_cost_yuan = Σ tariff_yuan_per_mwh × task_power_mw × overlap_dt_hours
```

积分分段边界至少包含任务开始/结束和电价变化边界。输入若为元/kWh，计费边界层先执行`tariff_yuan_per_mwh = 1000 × tariff_yuan_per_kwh`；当前`0.50~1.30`价格按该迁移规则处理。不得只改单位后缀而不换算数值。第一阶段使用统一线性增量功率，不把空闲功耗、PUE、非线性功耗或节点能效差异分摊给任务。CPU利用率加价只能进入单独的`congestion_score`或专门消融账本；无物理单位的优化信号必须命名为`cost_index`，不能写入`economic_cost_yuan`。

当前实际配置`TRAFFIC_DAY_DURATION_IN_SIM=288`、`SCHEDULING_CYCLE=0.005`时，一仿真单位为300秒，一周期为1.5秒。实现只能从统一时间换算器取得这些值，不得依赖`config.py`中陈旧的120秒/4.8秒注释。

主外生电价实验中：

```text
candidate_marginal_system_cost_yuan
= task_attributed_cost_yuan
= task_direct_energy_cost_yuan
```

含绿电补贴/碳税的状态相关计费实验中，候选特征使用加入前后节点总账之差；完成账本按同节点同时间任务功率比例分摊节点实际任务能源账单。边际成本不要求跨任务可加，归因成本必须可加且不依赖预约顺序。

### 7.5 启发式基线评分

第一条确定性等权基线可以使用：

```text
U(c) =
    0.5 × cost_score(c)
    + 0.5 × green_score(c)
    + w_balance × balance_score(c)
    - w_tardiness[sla_type] × preferred_start_tardiness_ratio(c)
```

其中：

```text
w_tardiness[Hard] = 0
w_tardiness[Soft] = w_soft_tardiness
w_tardiness[Flexible] = w_flexible_tardiness

green_score =
    0.5 × green_coverage
    + 0.5 × clip(green_absorption_delta / absorption_delta_scale, 0, 1)
```

`absorption_delta_scale`必须为正，并在查看正式测试结果前由训练pilot或物理范围冻结；默认1表示直接使用`[0,1]`吸纳率变化。该`U`只属于启发式基线和诊断，不是DQN必须复现的固定真值。

### 7.6 DQN评级

DQN对每个候选输出：

```text
Q(global_state, candidate_features)
```

Q值表示在当前状态选择该候选后，考虑后续任务到达分布和未来资源占用影响的期望累计回报。

需要特别说明：

- DQN不能看到真实未来任务；
- 它只能从训练分布中学习未来任务的统计影响；
- 候选局部成本最低不一定Q值最高，因为它可能占用未来紧缺资源；
- Q值不是物理可行性分数；
- 评估报告必须同时保留Q值和原始评价向量。

选择：

```text
selected_candidate = argmax Q(global_state, c)
```

若有相同Q值，使用`candidate_id`的确定顺序打破平局，保证复现。

## 8. DQN可变候选接口

### 8.1 前向接口

```text
q_values = policy.score_candidates(
    global_state,
    candidate_feature_matrix,
    candidate_mask
)
```

输出长度等于当前候选数量，不等于固定节点数量。

共享网络对每个候选使用同一参数：

```text
global_embedding = encode_global(global_state)
candidate_embedding_i = encode_candidate(features_i)
Q_i = q_head(concat(global_embedding, candidate_embedding_i))
```

候选顺序变化时，同一个候选的Q值应保持一致。

### 8.2 经验回放

```text
Transition:
    global_state_before
    selected_candidate_features
    reward
    global_state_after_commit
    next_candidate_set
    decision_time_sim
    next_transition_time_sim
    elapsed_seconds
    terminal
```

下一状态的Double-DQN最大值只在其可行候选集合中计算。

### 8.3 奖励可用时间

候选提交时可以准确知道：

- CPU/BW可行性；
- 计算和传输时间线；
- Soft迟到；
- 外生价格/绿电轨迹；
- 基于当前已知预约的成本与绿电估计。

但未来未知任务可能改变最终并发负载、绿电比例分摊和含负载因素的价格。训练需要区分“预约决策时钟”和“任务事件时钟”。

推荐的第一阶段奖励流水：

```text
r_commit = estimated_local_utility

r_completion_correction =
    realized_local_utility
    - estimated_local_utility
    + completion_outcome_reward

r_expired = expiration_penalty
r_failed = failure_penalty
```

流程：

1. 提交时创建`DecisionRecord`，保存估计指标、所选候选和提交后状态；
2. 当Completed/Expired/Failed等事件发生时，EventEngine把`(event_time_sim, reward, decision_id, event_type)`加入`system_event_reward_buffer`；
3. 在下一次调度决策的环境转移中，合并自上次决策以来的事件奖励；若长时间没有任务决策，应生成明确的时间推进转移，而不是丢失事件奖励；
4. 这样先前预约造成后续任务Expired的代价可以沿Bellman回报传播到先前动作；
5. `DecisionRecord`仍把实现值链接回原候选，用于审计、反事实和可选的专门延迟信用分配算法；
6. 不应在普通DQN中静默修改已经采样过的旧回放记录，除非明确实现了支持延迟奖励更新的回放协议；
7. 单独记录`realized-estimated`误差；
8. 正式评估只使用实现指标，不使用预约估计替代。

上述“估计+修正”使不折扣总量回到实现效用；折扣则自然反映结果发生时间。如果为了训练吞吐只使用预约时代理奖励，必须做“估计奖励vs实现修正奖励”消融，并不能用代理奖励报告最终性能。

### 8.4 连续时间折扣

标准“每调用一次`step`乘一次固定gamma”会让回报依赖同一周期内处理了多少任务，而不是实际经过时间。第一阶段统一使用：

```text
elapsed_seconds =
    (next_transition_time_sim - decision_time_sim)
    × seconds_per_sim_unit

gamma_elapsed = gamma_per_second ** elapsed_seconds

target = reward
    + (0 if terminal else gamma_elapsed × next_q)
```

如果在决策时刻`t0`和下一转移时刻`t1`之间缓冲了多个事件，转移内奖励为：

```text
transition_reward = immediate_reward_at_t0
    + Σ gamma_per_second ** event_elapsed_seconds_k × event_reward_k

event_elapsed_seconds_k =
    (event_time_sim_k - t0) × seconds_per_sim_unit
```

也可以在每个事件时刻显式生成时间推进转移；两种表示的目标值必须相同。

约束：

- 同一仿真时刻连续处理多个任务时`elapsed_seconds=0`，所以`gamma_elapsed=1`；
- 时间推进转移和完成/到期事件按真实经过秒数折扣；
- 事件缓冲的每条奖励必须携带时间戳，不能全部按下一决策时刻计时；
- `gamma_per_second`是训练参数，必须写入模型元数据；
- 不能同时再按决策步数重复乘固定gamma；
- 把同一物理轨迹拆成更多零时长决策，累计折扣结果必须不变。

### 8.5 没有当前DQN动作的系统结果

任务因为候选为空进入Pending或最终Expired时，当前任务没有可供DQN选择的动作，因此不能伪造一个WAIT动作来承载惩罚。处理方式是：

- Pending转换本身只记录状态，不虚构成功/失败候选；
- Expired、队列容量拒绝和预约失效形成系统事件奖励与约束成本；
- 这些事件进入后续环境转移，使造成资源挤占的历史动作通过累计回报受到影响；
- 评估中仍按任务状态直接计数，不依赖奖励是否成功传播。

## 9. 原子提交

### 9.1 提交流程

```text
try_commit(candidate):
    lock_or_compare_snapshot_version()

    recheck CPU [compute_start, compute_end)
    recheck every path edge [tx_start, tx_end)

    if any check fails:
        write nothing
        return CONFLICT

    write CPU reservation
    write all edge reservations
    increment reservation version
    freeze reservation fields
    return COMMITTED
```

### 9.2 提交冲突

若候选生成到提交之间资源版本改变：

- 不得只保留CPU或部分链路；
- 使用最新快照重新生成或重新验证候选；
- 技术冲突重试使用`commit_attempts`，不增加任务`failure_retry_count`；
- 单线程第一阶段理论上冲突应为0，但接口仍必须保证原子性；
- `commit_attempts < MAX_COMMIT_ATTEMPTS_PER_DECISION`时可用新快照重新生成/提交；
- 达到上限后任务回到Queued，不得无限自旋，也不得被记成资源不可行或业务失败；若绝对截止已到则按统一到期规则进入Expired。

## 10. 事件推进与实现值核算

### 10.0 同一时间戳事件批次

`advance_to(t)`把同一时间戳作为原子批次处理：

```text
integrate [previous_time, t)
→ release intervals ending at t and settle terminal events
→ activate pre-existing reservations starting at t
→ materialize arrivals/reactivations at t
→ process eligible queue in deterministic EDF order
→ activate newly committed intervals whose start equals t
→ expire still-uncommitted tasks whose closed deadline is t
→ emit one post-batch state/metric snapshot
```

在闭截止边界`t`，任务先获得一次恰好在`t`开始的机会，之后才能Expired。每次同刻提交更新日历，后续任务使用新版本；这些决策`elapsed_seconds=0`。批次内部可以记录每决策日志，但系统利用率、状态守恒和硬不变量快照只在全部同刻转换完成后生成，避免把瞬态顺序当作物理并发。

### 10.1 远程任务

```text
Reserved
  -- at transmission_start --> Transmitting
  -- at compute_start      --> Running
  -- at compute_end        --> Completed
```

### 10.2 本地任务

```text
Reserved
  -- at compute_start --> Running
  -- at compute_end   --> Completed
```

### 10.3 资源语义

- 预约日历在提交时已经占用未来容量；
- 实时`used`可以用于展示当前运行状态，但不能替代预约日历做未来可行性；
- 带宽在传输结束立即释放；
- CPU在计算结束立即释放；
- 完成释放不等于取消预约；
- 事件时间相同时按“结束释放 → 开始占用”处理，与半开区间一致。

### 10.4 绿电最终归因

在节点`j`、时刻`t`：

```text
coverage_ratio_j(t) =
    min(1, green_supply_j(t) / total_compute_power_j(t))

task_attributed_green_power_i(t) =
    task_power_i(t) × coverage_ratio_j(t)
```

对执行区间积分得到任务绿电MWh。该分摊满足：

```text
Σ task_attributed_green_power_i(t)
= min(total_compute_power_j(t), green_supply_j(t))
```

因此不依赖任务预约先后顺序。

最终账本字段命名为`task_attributed_green_energy_mwh`。候选评级中的`estimated_green_absorption_delta`使用另一条反事实链路：

```text
candidate_marginal_green_energy_mwh =
    green_used_with_candidate_mwh
    - green_used_without_candidate_mwh

green_absorption_delta =
    candidate_marginal_green_energy_mwh
    / green_supply_mwh_over_interval
    if green_supply_mwh_over_interval > 0
```

若供给为0，实现吸纳率/变化为`NOT_APPLICABLE(null)`；候选特征使用中性0并记录`green_opportunity=false`。两类量不得复用字段。当候选加入前绿电已经100%吸纳时，候选的边际吸纳为0，但其最终比例归因绿电仍可大于0。比例归因要求跨任务可加；边际反事实不要求跨任务可加。

### 10.5 成本实现值核算

完成核算器使用任务真实`[compute_start, compute_end)`与该区间的电价分段，按第7.4节公式生成：

```text
task_energy_mwh
economic_cost_yuan
```

预约时估计值和完成时实现值使用同一单位与积分器；二者差异只能来自预约后新到达任务影响的内生分摊或明确版本化的计费规则，不能来自一处按仿真单位、一处按小时。外生电价模式下，若任务功率与价格均不依赖后续任务，则估计成本与实现成本必须完全一致。

## 11. 主动等待如何定义和验证

### 11.1 不是独立动作

```text
active_wait = selected.compute_start - earliest_feasible_start
```

- `0`：最早可行执行；
- `>0`：主动等待；
- 无候选进入Pending，不叫主动等待；
- 因本周期尚未轮到处理产生的是`scheduler_queue_delay`，不叫主动等待。

完整时间分解：

```text
scheduler_queue_delay = decision_time - arrival_time
earliest_feasibility_lead = earliest_feasible_start - decision_time
active_wait = selected.compute_start - earliest_feasible_start
reservation_lead = selected.compute_start - decision_time

start_delay = scheduler_queue_delay
            + earliest_feasibility_lead
            + active_wait
```

`earliest_feasibility_lead`已经包含JIT传输、网格对齐和资源可用性影响；不得再把传输时间重复加到`start_delay`。所有分量使用同一仿真时间单位，并在输出时可统一换算为秒。

### 11.2 局部反事实

对当前策略：

```text
c_selected = 全部可行候选中的策略最优
c_earliest = 最早开始候选集合中的同偏好最优
```

记录：

```text
additional_delay
estimated_cost_change
estimated_green_coverage_change
estimated_absorption_change
estimated_balance_change
preferred_start_tardiness_ratio_change
```

任务完成后再记录对应实现值变化或系统级归因。

### 11.3 系统级反事实

局部收益不能证明整个系统受益。正式结论来自：

```text
同一任务轨迹
同一外生价格/绿电
同一任务队列顺序
同一初始资源

EarliestFeasiblePolicy
vs.
FutureReservationPolicy
```

逐seed比较真实完成率、经济成本、绿能、SLA和负载，并按需求第14.8节做配对区间和工程门槛判定。

### 11.4 正式评估结算

```text
phase A: arrivals
    生成冻结trace中arrival_time <= arrival_cutoff的任务

phase B: admission settlement
    禁止新到达
    继续处理已到达Queued/Pending和事件
    直到所有已到达任务均为Reserved/Rejected/Expired

phase C: execution drain
    禁止新到达和新业务任务
    推进Reserved/Transmitting/Running
    直到全部Completed/Failed
```

三阶段可以由同一事件循环自然交错推进，但最终必须满足：

```text
queued_count_at_end = 0
pending_count_at_end = 0
reserved_or_running_count_at_end = 0
```

若`evaluation_safety_cap`触发，运行状态为`INVALID_INCOMPLETE_SETTLEMENT`，不得产出正式通过结论。安全上限是故障保护，不是统计截尾窗口。

## 12. 端到端算例

以下使用物理秒展示，并采用当前配置派生的`1.5秒`调度周期。正式实现仍以仿真时间存储，通过统一转换器显示为秒。全局调度网格锚点为0，因此合法网格点是`..., 99, 100.5, 102, ...`。

### 12.1 任务和绝对窗口

```text
到达时间 a = 99秒
决策时间 d = 100.5秒
类型 = Soft
偏好启动限制 L = 20秒
绝对启动限制 = 1.2L = 24秒
绝对偏好启动时间 = 119秒
绝对最晚启动时间 = 123秒

数据量 = 100MB（十进制）
预留带宽 = 100Mbps
远程路径长度 = 1000km
CPU需求 = 4
执行时长 = 60秒
CPU增量功率 = 0.01MW/CPU
```

远程传输时间：

```text
数据发送时间 = 8 × 100MB / 100Mbps = 8秒
传播时间 = 1000km / 200000km/s = 0.005秒
T_tx = 8.005秒
```

在不考虑资源占用时，远程JIT最早网格点为：

```text
ceil_to_global_cycle(100.5 + 8.005, 1.5, anchor=0)
= ceil_to_global_cycle(108.505, 1.5, anchor=0)
= 109.5秒
```

绝对截止`123秒`恰好对齐网格，因此该网格点可被枚举；下一个`124.5秒`不能作为候选。对每个声明节点和路径，正式模式枚举窗口内所有网格点，再由CPU/BW日历过滤。下表只抽取四个代表点说明计算，不能据此对完整集合做Top-K裁剪。

### 12.2 代表候选和硬过滤

任务功率和能量为：

```text
task_power = 4 × 0.01MW = 0.04MW
task_energy = 0.04MW × 60/3600h = 0.000666667MWh
```

| 候选 | 计算开始 | 传输 | 外生电价 | 经济成本 | 绿电覆盖 | 归一化吸纳增量 | 容量余量 | 启动时延 | Soft迟到 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| A：本地 | 109.5秒 | 0 | 1200元/MWh | 0.80元 | 20% | 0.10 | 40% | 10.5秒 | 0 |
| B：远程 | 112.5秒 | 8.005秒 | 900元/MWh | 0.60元 | 90% | 0.40 | 50% | 13.5秒 | 0 |
| C：远程 | 121.5秒 | 8.005秒 | 600元/MWh | 0.40元 | 100% | 0.50 | 60% | 22.5秒 | 0.625 |
| D：远程 | 124.5秒 | 8.005秒 | 450元/MWh | 0.30元 | 100% | 0.60 | 60% | 25.5秒 | 不可行 |

传输区间 = [112.5 - 8.005, 112.5) = [104.495, 112.5)
计算区间 = [112.5, 172.5)
```

```

### 12.3 等待分解和评级

假定资源日历过滤后，全局最早可行开始为A的`109.5秒`：

```text
s_earliest = 109.5秒
scheduler_queue_delay = 100.5 - 99 = 1.5秒
earliest_feasibility_lead = 109.5 - 100.5 = 9秒

active_wait(A) = 0秒
active_wait(B) = 3秒
active_wait(C) = 12秒

start_delay(B) = 1.5 + 9 + 3 = 13.5秒
```

这说明系统不先执行独立的“是否WAIT”判断。策略直接在完整可行候选中选择；选择B就等价于相对A主动等待3秒。

下面仅演示确定性等权启发式，不冻结正式训练参数。假定训练前固定：

```text
reference_marginal_cost = 0.80元
cost_scale = 0.80元
w_balance = 0.10
w_soft_tardiness = 0.40
```

则：

| 候选 | cost_score | green_score | balance_score | preferred_start_tardiness_ratio | U(c) |
| --- | ---: | ---: | ---: | ---: | ---: |
| A | 0.00 | 0.15 | 0.40 | 0 | 0.115 |
| B | 0.25 | 0.65 | 0.50 | 0 | 0.500 |
| C | 0.50 | 0.75 | 0.60 | 0.625 | 0.435 |

在这个示例参数下：

- 最早基线选择A；
- 等权启发式选择B；
- 偏绿策略可能选择C，但必须显式承担Soft迟到；
- 候选D不会因为价格低而重新进入集合；
- DQN不以`U(c)`为真值，而是分别输出`Q(global_state,c)`，同时保留上表所有原始量用于审计。

若DQN选择B，局部等待反事实相对A为：

```text
成本节省 = 0.80 - 0.60 = 0.20元
绿电覆盖变化 = 0.90 - 0.20 = +0.70
归一化吸纳增量变化 = 0.40 - 0.10 = +0.30
容量余量变化 = 0.50 - 0.40 = +0.10
主动等待增加 = 3秒
Soft迟到变化 = 0
```

这个向量是局部解释；正式机制收益仍需在相同任务轨迹下，将未来预约策略与强制最早策略做系统级配对。

### 12.4 原子提交和生命周期

若B由资源快照版本7生成，提交时日历仍为版本7，则一次事务写入：

```text
BW: path(B), [104.495,112.5), 100Mbps
CPU: node(B), [112.5,172.5), 4CPU
```

状态路径：

```text
Arrived(99)
→ Queued
→ Reserved(100.5，原子提交成功)
→ Transmitting(104.495)
→ Running(112.5)
→ Completed(172.5)
```

`Reserved`时只增加accepted，不增加completed。任务到`172.5秒`完成后，账本才按完整执行区间核算实现成本和绿电、追加实现值修正并增加completed。

若提交前另一任务使日历变成版本8，结果必须为`CONFLICT`且CPU/BW零写入。调度器使用新快照重新生成候选；本次决策的有限`commit_attempts`用尽后回到Queued，不能把冲突记成任务失败或提高业务优先级。

### 12.5 无候选不是WAIT动作

若任务在完整绝对窗口内因动态预约暂时没有候选：

```text
Queued → PendingUncommitted
```

它不占CPU/BW、不算accepted，也不生成虚构的DQN WAIT动作。窗口内出现资源释放、事务回滚或容量恢复事件时重新搜索；没有相关状态变化时不逐周期重复同一完整搜索。到`123秒`仍没有候选则：

```text
PendingUncommitted → Expired(ABSOLUTE_START_DEADLINE)
```

如果任务一开始就字段非法，或者CPU/BW需求超过系统任何节点/路径的静态上限，才使用确定性`Rejected`，不能与动态无候选混为一个drop计数。

## 13. 候选规模和完整性

未压缩候选上界近似为：

```text
node_count × paths_per_node × time_slot_count
```

正式v1.0运行必须完整枚举上述规模，不得在生成阶段按时间采样，也不得在交给策略前按人工总分Top-K。实现应先通过向量化区间查询、缓存、批量候选特征计算和共享网络批推理降低开销。

仅在独立的`approximate`可扩展性实验中，才允许按以下方式压缩：

1. 先做硬过滤；
2. 保留最早候选集合；
3. 保留最低成本、最高覆盖、最高吸纳、最均衡候选；
4. 保留Pareto非支配候选；
5. 再在相似候选中做时间分层采样；
6. 记录理论规模、过滤后规模、压缩后规模、遗漏率、代表性覆盖和相对完整集合的最优候选遗憾。

近似模型、回放和结果文件必须带独立模式标记，不能与正式完整窗口结果混合。不能先按固定人工总分取Top-K，否则DQN只是在人工评分预选后的狭窄集合中选择。

## 14. 必须保持的不变量

每次调度周期结束后必须断言：

```text
I-01 任意节点任意时刻reserved_cpu <= cpu_capacity
I-02 任意链路任意时刻reserved_bw <= link_capacity
I-03 CPU和BW没有部分提交
I-04 每个Reserved任务都有完整不可变预约
I-05 transmission_end == compute_start
I-06 transmission_start >= decision_time
I-07 compute_end == compute_start + execution_duration
I-08 Hard/Soft/Flexible绝对启动限制零违规
I-09 Completed只能由Running到达compute_end产生
I-10 Pending任务不占资源、不计accepted
I-11 改变同批任务预约遍历顺序不改变最终绿电分摊账本
I-12 调度输入不包含尚未到达任务
I-13 所有策略读取相同任务队列顺序
I-14 状态计数满足任务守恒
I-15 economic_cost_yuan和task_energy_mwh均由仿真时长显式换算小时后积分
I-16 正式模式实际枚举时间槽数等于声明路径集合上的理论完整网格数
I-17 折扣只由物理elapsed_seconds决定，不因同一时刻决策拆分数量改变
I-18 每个Reserved任务的start_delay严格等于queue_delay+earliest_feasibility_lead+active_wait
I-19 同一时间戳事件批次顺序确定、闭截止先调度后到期，重复advance_to(t)幂等
```

## 15. 与当前代码接口的主要迁移

| 当前接口 | 问题 | 目标接口 |
| --- | --- | --- |
| `calculate_priority()` | SLA倍率和retry改变任务顺序 | `queue_order_key()`使用绝对期限及确定平局规则 |
| `_candidate_times_for_task()` | 先生成统一时间，未按路径传输确定最早JIT开始 | 节点/路径确定传输时长后生成该路径时间网格 |
| `evaluate_schedule_candidates()` | 同时做可行性、人工总分和当前节点动作映射 | `CandidateGenerator.generate()`输出完整候选与原始向量 |
| `estimate_wait_opportunity()` | 只比较人工标量总分 | `CounterfactualLogger`保存同偏好最早候选与收益向量 |
| 固定节点+WAIT动作 | 不能直接选择未来候选 | `CandidatePolicy.score_candidates()` |
| `env.step(node_action)` | 环境再次替策略选时间/路径 | `ReservationManager.try_commit(candidate_id)` |
| `add_success_allocation()` | 调度成功后分步写资源 | 原子事务内同时写CPU/BW |
| `update_active_tasks()` | started布尔值且完成不计数 | `EventEngine`显式状态转换与Completed事件 |
| `record_success()` | 预约即算完成 | `record_reserved()`与`record_completed()`分开 |

## 16. 已冻结业务选择

本设计实现以下已确认结论：

1. F-01：Soft约束计算开始，不约束完成；
2. F-02：`None`改为偏好`L`、绝对上限`1.5L`且线性迟到的`Flexible`；
3. F-03：固定预留带宽的流水线传输；
4. F-04：在线逐任务预约和绝对期限优先队列；
5. F-05：绿电最终按并发任务功率比例归因。
6. F-06：统一线性增量CPU功率，并按元/MWh×MW×小时核算经济成本。
7. F-07：候选非空时禁止学习式主动拒绝，所有策略使用相同确定性接纳规则。

本文已经是算法设计基线。网络层数、奖励系数和候选路径K值仍属于实现/实验参数；候选Top-K只允许用于独立近似实验，正式完整窗口模式不使用Top-K。运行代码修改仍需另行授权。
