## 0. 判定规则

本矩阵只回答“用户在源文档中的每一项结论、疑问或方案请求，是否被v1.0正确承接”。判定含义：

- **完整承接**：用户结论已经以相同语义进入v1.0，并有R需求和测试证据；
- **完整承接并闭合**：源文档要求提供方案或存在歧义，v1.0已记录用户对最终方案的明确结论；
- **后续阶段**：用户明确不在第一阶段处理；
- **禁止弱化**：后续设计和代码不能把该源结论降级为奖励偏好或实现参数。

引用行号以当前工作区源文件为准。

## 3. 用户“不理解/需要方案”部分的回答状态

### 3.1 传输时间

已确认方案：

```text
T_data_sec = 8 × data_size_MB / bandwidth_demand_Mbps
T_prop_sec = Σ distance_km / fiber_speed_km_per_sec
T_tx_sim = (T_data_sec + T_prop_sec) / seconds_per_sim_unit
```

路径容量的作用是硬可行性：每条边静态容量和传输区间剩余容量均不得小于`bandwidth_demand`。第一阶段预约后任务速度不再随新任务改变。该方案已由F-03冻结。

### 3.2 DQN动作设计

已给出的设计思路：

```text
CandidateGenerator -> 完整可行候选集合
CandidatePolicy -> 对每个候选计算Q(global_state, candidate)
ReservationManager -> 原子提交选中candidate_id
```

动作不再是固定“节点+WAIT”；等待由候选开始时间自然表达。F-07已冻结候选非空时必须选择一个候选。预约估计与完成实现奖励通过时间戳事件转移连接，折扣按物理`elapsed_seconds`计算，不随同一时刻任务决策数量改变。

### 3.3 None到Flexible迁移

源文档中的“None任务在SLA约束范围内”已经通过F-02闭合：

- 规范名称改为`Flexible`；
- 旧`latency_limit`解释为偏好启动时限`L`；
- 绝对最晚启动时间派生为`1.5L`；
- `(L,1.5L]`采用线性迟到；
- 无候选Pending，到期Expired；
- 第一阶段不引入无截止类型或外部无限批处理队列。
